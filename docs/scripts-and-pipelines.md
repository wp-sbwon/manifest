# Scripts and pipelines

How data in `.manifest/` is created and refreshed. The view app only reads; it does not write these files.

## Bottom-up (code → .manifest)

**Script:** `scripts/run_bottom_up_docs.py`

- **Input:** Project root, manifest dir (e.g. `--project-root <path> --manifest-dir <path>/.manifest`).
- **Writes:**
  - `blueprint_code.json` – always (CodeExtractor from codebase).
- **Also:** Can write `state.json` → `health_metrics` (code quality, test coverage, binary size) when the pipeline runs health collection.

**Principle:** The bottom-up pipeline produces `blueprint_code.json` from the actual codebase (AST/code extraction). That file should be an **exact reflection of the current code** — same schema as design so the view can compare and show status; content derived only from the code, not hand-written. Do not hand-write `blueprint_code.json`; regenerate with this script or via CodeWatcher/CodeExtractor.

```bash
python scripts/run_bottom_up_docs.py --project-root <project> --manifest-dir <project>/.manifest
python scripts/run_bottom_up_docs.py --project-root <project> --manifest-dir <project>/.manifest
```

## Top-down (design → .manifest)

**Agents / tools** (e.g. Architect) write:

- `prd.json` – product requirements.
- `blueprint_design.json` – blueprint (root intent: mission, goals, interface; entities with id, children, intent, reality, etc.).
- `tasks.json` – task list.

No single “top-down script”; creation is via core APIs or agent workflows that write these files.

## Status (diagram + header)

**Not a file.** The view app computes status when it loads:

- BlueprintSynchronizer compares `blueprint_design.json` vs `blueprint_code.json` → `component_statuses`.
- Diagram and header STATUS use this in-memory result.

So: keep blueprint and blueprint_code in sync (same component ids/names); run bottom-up when code changes; view will show updated status on refresh (S).

## Tmp (dev) mock blueprint data

When developing in the manifest repo, the view can use the **tmp** project so it doesn’t load the full manifest codebase. The tmp project is a small calculator app under `tmp/` with mock blueprint data.

**Script:** `scripts/create_mock_project_data.py`

- **Writes:** `tmp/.manifest/blueprint_design.json`, `tmp/.manifest/blueprint_code.json` (entity schema: root + cli, arithmetic_engine, output; L2: add, sub, mul), plus `prd.json`, `tasks.json`, `state.json`.
- **Usage:** From repo root, `PYTHONPATH=src python scripts/create_mock_project_data.py` (defaults to `tmp/.manifest`) or pass a path.

**Note:** The tmp code blueprint is **hand-crafted** (a subset of design entities) to demo a planned/done status mix. It is **not** produced by code extraction. In a real project, `blueprint_code.json` should be generated by the bottom-up pipeline from the actual codebase so it is an exact reflection of the code (see Bottom-up above). The **tmp source code** under `tmp/` is kept aligned with this mock: only cli, arithmetic_engine, add, sub are implemented in code; output and mul are planned (main does not use the formatter; mul raises NotImplementedError). See `tmp/README.md`.

**Planned vs done:** The code blueprint includes only some entities (root, cli, arithmetic_engine, add, sub). Omitted entities (e.g. **output**, **mul**) show as **planned** in the diagram and header; the rest show as **healthy/done**. To change which are done, edit `_CODE_IMPLEMENTED_IDS` in the script and re-run it.

To refresh tmp blueprint data after changing the script or schema, run:

```bash
PYTHONPATH=src python scripts/create_mock_project_data.py tmp/.manifest
```

Then run the view with tmp: `MANIFEST_DEV=1 PYTHONPATH=src python -m manifest` or `PYTHONPATH=src python -m manifest.view.app --manifest-dir tmp/.manifest`.
