# PRD (Product Requirements Document) Template

This template defines the required structure for all PRD documents generated by the Orchestrator. The Orchestrator must ensure all sections are completed during ideation.

## Required Sections

### 1. Overview
**Purpose**: High-level description of the product/feature

**Required Content**:
- Product/Feature name
- Primary goal
- Target users
- Success metrics

### 2. User Flows
**Purpose**: Detailed user interaction scenarios

**Required Content**:
- List of user personas
- For each persona:
  - Primary use cases
  - Step-by-step user flow
  - Entry points
  - Exit points
  - Error handling scenarios

**Example Structure**:
```markdown
### Persona: Developer
- Use Case: Create a new feature
  - Flow:
    1. User opens Manifest
    2. User starts ideation with Orchestrator
    3. Orchestrator asks clarifying questions
    4. User provides answers
    5. Orchestrator generates PRD
    6. User reviews and approves
  - Entry Point: Main chat interface
  - Exit Point: PRD approval
  - Error Handling: If PRD incomplete, Orchestrator asks for missing information
```

### 3. Technical Constraints
**Purpose**: Technical limitations and requirements

**Required Content**:
- Technology stack constraints
- Performance requirements
- Scalability requirements
- Security requirements
- Integration constraints
- Resource limitations

### 4. Success Criteria
**Purpose**: Measurable outcomes that define success

**Required Content**:
- Functional requirements (must-have features)
- Non-functional requirements (performance, reliability, etc.)
- Acceptance criteria
- Definition of Done

### 5. Architecture Requirements
**Purpose**: High-level architectural decisions

**Required Content**:
- System architecture overview
- Component interactions
- Data flow
- Integration points

### 6. Dependencies
**Purpose**: External dependencies and prerequisites

**Required Content**:
- External services/APIs
- Third-party libraries
- Infrastructure requirements
- Team dependencies

## Validation Checklist

The Orchestrator must verify the following before finalizing a PRD:

- [ ] Overview section is complete
- [ ] At least one user flow is defined for each identified persona
- [ ] Technical constraints are documented
- [ ] Success criteria are measurable and specific
- [ ] Architecture requirements are outlined
- [ ] Dependencies are identified
- [ ] All sections contain substantive content (not just placeholders)

## Notes

- PRD is the foundation for Architecture and Blueprint generation
- Incomplete PRDs will result in incomplete Architecture/Blueprint
- User flows are critical for understanding the product from the user's perspective
- Technical constraints help prevent unrealistic implementations
